Behavior Trees

Design intelligent AI behaviors using the Blastback Engine's data-driven behavior tree system. Define complex decision-making logic entirely in JSON.

What Are Behavior Trees?

Behavior trees (BTs) are a hierarchical model for organizing AI decision-making. Unlike finite state machines, behavior trees offer a modular, composable structure that scales gracefully from simple patrol routines to elaborate boss fight sequences.

Blastback Engine uses behavior trees as the primary AI system because they provide:

  • Modularity — individual sub-trees can be reused across many entity types.
  • Readability — the tree structure maps directly to how designers think about AI priorities.
  • Data-driven authoring — trees are plain JSON files, editable by hand or with the visual editor.
  • Runtime flexibility — the resolution system lets entities override specific nodes without duplicating the whole tree.
Note
Every tick, the behavior tree is evaluated from the root. Each node returns one of three statuses: Success, Failure, or Running. The parent node uses these statuses to decide which child to evaluate next.

Creating Behavior Tree Files

Behavior tree files follow a strict naming convention so the engine can discover and load them automatically:

bt.[ID].json

The [ID] portion becomes the identifier you reference from an entity's ai component via templateID.

Example file names
bt.basic_chase.json
bt.patrol_and_attack.json
bt.boss_phase1.json
Important
The bt. prefix is mandatory. Without it, the engine will not recognize the file as a behavior tree definition.

BT Node Structure

Every node in a Blastback behavior tree is a JSON object with a specific set of fields. The node's role in the tree is determined by its type, which is encoded in the key name when the node appears as a child.

Node JSON Schema

FieldTypeRequiredDescription
commandsstring[]NoList of command strings executed when the node is reached. Commands that perform checks return Success or Failure.
childrenobjectNoDictionary of child nodes. Keys use the format type.name to encode the child's node type and identifier.
parametersobjectNoConfiguration parameters for decorator nodes (e.g., repeat count, cooldown time).
Basic node structure
{
  "commands": ["ai.checkPlayerInRange 120"],
  "children": {
    "action.chasePlayer": {
      "commands": ["ai.moveToTarget player"]
    },
    "action.idle": {
      "commands": ["entity.animate idle,loop"]
    }
  }
}

Node Types

The node type is identified by the key prefix in the children dictionary. The format is type.name, where type determines the node's evaluation behavior and name is a unique identifier.

Type PrefixNode TypeDescription
sequenceSequenceRuns children left to right. Stops and returns Failure if any child fails. Returns Success only if all children succeed.
selectorSelectorRuns children left to right. Stops and returns Success if any child succeeds. Returns Failure only if all children fail.
actionActionA leaf node that executes its commands. Returns the result of the last command.
decoratorDecoratorWraps a single child and modifies its result based on parameters (e.g., invert, repeat, cooldown).
conditionConditionEvaluates a check command. Returns Success if the condition is met, Failure otherwise. Does not execute side-effect actions.

Node Type Identification via Children Key

The children key in a node is a dictionary where each key follows the type.name pattern. The engine parses the prefix before the first dot to determine the node type, and uses the portion after the dot as the node's unique identifier within the tree.

Node type identification examples
"children": {
  "selector.mainBehavior": { ... },
  "sequence.attackRoutine": { ... },
  "action.flee": { ... },
  "decorator.repeatForever": { ... },
  "condition.isPlayerClose": { ... }
}
Note
The name portion of the key (after the dot) is used as the nodeID for AI events and for the resolution system. Choose descriptive, unique names so you can easily target specific nodes for overrides and event listeners.

Commands in Nodes

The commands array contains command strings that are executed when the node is evaluated. Commands serve two purposes:

  1. Condition checks — commands that test a condition and return Success or Failure, controlling tree traversal.
  2. Actions — commands that perform side effects (move, animate, attack) and return a status.

When a node has multiple commands, they are executed in order. If any command returns Failure, the node immediately returns Failure without executing the remaining commands.

CommandTypeDescriptionReturns
ai.checkPlayerInRange <distance>ConditionChecks if the player is within the specified pixel distance.Success / Failure
ai.moveToTarget <targetType>ActionMoves the entity toward the specified target.Running / Success
ai.wait <seconds>ActionWaits for the specified duration.Running / Success
ai.setTarget <targetType>ActionSets the current AI target for subsequent commands.Success
ai.checkHealth <threshold>ConditionChecks if entity health is above the threshold.Success / Failure
ai.patrol <distance>ActionPatrols back and forth within the given distance from the spawn point.Running
ai.flee <distance>ActionMoves the entity away from the current target.Running / Success
entity.emit <eventID>ActionEmits an event on the entity.Success
entity.animate <anim>,<mode>ActionPlays an animation on the entity.Success
Tip
You can chain a condition check before an action in the same node's commands array. If the condition fails, the action is never executed, and the node returns Failure immediately. This is a concise alternative to using a separate condition child node.

Parameters for Decorator Nodes

Decorator nodes use the parameters object to configure their wrapping behavior. The available parameters depend on the decorator subtype.

ParameterTypeDescription
repeatCountintNumber of times to repeat the child. Use -1 for infinite repetition.
cooldownfloatMinimum seconds between executions of the child node.
invertboolIf true, inverts the child's Success/Failure result.
succeedAlwaysboolIf true, always returns Success regardless of the child's result.
Decorator with parameters
"decorator.repeatPatrol": {
  "parameters": {
    "repeatCount": -1
  },
  "children": {
    "action.patrolStep": {
      "commands": ["ai.patrol 80"]
    }
  }
}
Cooldown decorator example
"decorator.attackCooldown": {
  "parameters": {
    "cooldown": 1.5
  },
  "children": {
    "action.attack": {
      "commands": [
        "entity.animate attack,once",
        "entity.emit meleeAttack"
      ]
    }
  }
}

Inline Templates vs. Referenced templateID

There are two ways to assign a behavior tree to an entity's ai component:

Referenced Template (Recommended)

Point to an external bt.[ID].json file using templateID. This is the preferred approach for reusable behaviors shared across multiple entities.

Entity AI component with templateID
"ai": {
  "templateID": "patrol_and_attack"
}

The engine will look for a file named bt.patrol_and_attack.json and load its tree definition.

Inline Template

Define the tree directly inside the entity JSON. Useful for one-off behaviors unique to a single entity.

Entity AI component with inline tree
"ai": {
  "tree": {
    "children": {
      "selector.root": {
        "children": {
          "sequence.chase": {
            "children": {
              "condition.playerNearby": {
                "commands": ["ai.checkPlayerInRange 80"]
              },
              "action.pursue": {
                "commands": ["ai.moveToTarget player"]
              }
            }
          },
          "action.idle": {
            "commands": ["entity.animate idle,loop"]
          }
        }
      }
    }
  }
}
Note
Inline templates cannot be shared across entities. If you find yourself duplicating an inline tree, extract it into a bt.[ID].json file and use templateID instead.

The Resolution System

The resolution system is the key to creating modular, reusable AI. It allows entities to override specific nodes in a referenced behavior tree without duplicating the entire tree.

When an entity references a templateID, it can provide a resolution object that maps node names to replacement definitions. The engine merges the resolution into the base tree at load time.

Entity with resolution overrides
"ai": {
  "templateID": "patrol_and_attack",
  "resolution": {
    "attackAction": {
      "commands": [
        "entity.animate slash,once",
        "entity.emit meleeAttack"
      ]
    },
    "patrolStep": {
      "commands": ["ai.patrol 120"]
    }
  }
}

In the base tree bt.patrol_and_attack.json, any node whose name portion (the part after the dot in type.name) matches a key in resolution will have its commands (and optionally children) replaced by the resolution entry.

Tip
Design your base behavior trees with clearly named "hook" nodes that you expect entities to override. For example, name your attack node action.attackAction so every entity can provide its own attack commands via resolution without touching the tree structure.

Resolution in Practice

Consider a base tree used by all melee enemies. Two different enemies override it differently:

Goblin uses a sword slash
"ai": {
  "templateID": "melee_enemy",
  "resolution": {
    "attackAction": {
      "commands": ["entity.animate sword_slash,once"]
    }
  }
}
Troll uses a ground pound
"ai": {
  "templateID": "melee_enemy",
  "resolution": {
    "attackAction": {
      "commands": [
        "entity.animate ground_pound,once",
        "entity.emit aoeAttack"
      ]
    }
  }
}

AI Component Events

The AI system emits events when specific nodes start and end execution. These events follow the naming convention:

ai.{nodeID}.onStart
ai.{nodeID}.onEnd

Where {nodeID} is the name portion of the node key (e.g., for action.chasePlayer, the nodeID is chasePlayer).

Event PatternDescription
ai.{nodeID}.onStartFires when the node begins execution for the first time in a traversal.
ai.{nodeID}.onEndFires when the node completes execution (returns Success or Failure, not Running).

These events can be captured by the entity's commandMap or model events to trigger animations, sounds, or other effects synchronized with AI state changes.

Reacting to AI events in an entity model
"model": {
  "events": {
    "ai.chasePlayer.onStart": {
      "playSound": { "id": "enemy_alert" }
    },
    "ai.chasePlayer.onEnd": {
      "playSound": { "id": "enemy_lost_target" }
    },
    "ai.attackAction.onStart": {
      "spawnEffect": { "id": "attack_telegraph" }
    }
  }
}
Reacting to AI events via commandMap
"components": {
  "mob": {
    "commandMap": {
      "ai.chasePlayer.onStart": "entity.animate run,loop",
      "ai.patrolStep.onStart": "entity.animate walk,loop",
      "ai.idle.onStart": "entity.animate idle,loop"
    }
  }
}

Online AI Editor

Blastback provides a visual behavior tree editor that lets you design, test, and export trees without editing JSON by hand.

Open the Online AI Editor

The editor supports:

  • Drag-and-drop node placement and rearrangement
  • Real-time tree validation and error highlighting
  • Export directly to bt.[ID].json format
  • Import existing trees for editing and iteration
  • Visual debugging with simulated tick execution
  • Node search and filtering for large trees
Tip
The online editor is the fastest way to prototype complex behavior trees. Design your tree visually, export it, and then fine-tune the JSON if needed.

Complete Example: Patrol and Chase

Here is a complete behavior tree that implements a patrol-and-chase pattern. The entity patrols a fixed area, and when the player comes within range, it switches to chasing and attacking.

bt.patrol_and_chase.json
{
  "children": {
    "selector.root": {
      "children": {
        "sequence.chaseAndAttack": {
          "children": {
            "condition.playerInRange": {
              "commands": ["ai.checkPlayerInRange 100"]
            },
            "action.setPlayerTarget": {
              "commands": ["ai.setTarget player"]
            },
            "selector.engageBehavior": {
              "children": {
                "sequence.attackIfClose": {
                  "children": {
                    "condition.inAttackRange": {
                      "commands": ["ai.checkPlayerInRange 24"]
                    },
                    "action.attackAction": {
                      "commands": [
                        "entity.animate attack,once",
                        "entity.emit meleeAttack"
                      ]
                    },
                    "action.attackCooldown": {
                      "commands": ["ai.wait 0.8"]
                    }
                  }
                },
                "action.chasePlayer": {
                  "commands": [
                    "entity.animate walk,loop",
                    "ai.moveToTarget player"
                  ]
                }
              }
            }
          }
        },
        "decorator.repeatPatrol": {
          "parameters": {
            "repeatCount": -1
          },
          "children": {
            "sequence.patrolLoop": {
              "children": {
                "action.patrolStep": {
                  "commands": [
                    "entity.animate walk,loop",
                    "ai.patrol 80"
                  ]
                },
                "action.patrolPause": {
                  "commands": [
                    "entity.animate idle,loop",
                    "ai.wait 2.0"
                  ]
                }
              }
            }
          }
        }
      }
    }
  }
}

How This Tree Works

  1. The root selector tries the chase-and-attack sequence first.
  2. The condition.playerInRange node checks if the player is within 100 pixels. If the check fails, the entire sequence.chaseAndAttack fails, and the selector moves to the patrol branch.
  3. If the player is in range, the entity sets the player as its target and enters the engage selector.
  4. The engage selector first tries to attack (if the player is within 24 pixels), then falls back to chasing.
  5. If no player is nearby, the patrol decorator repeats indefinitely: walk 80 pixels, pause for 2 seconds, then repeat.

Using This Tree with an Entity

enemy_guard.mob.json (excerpt)
"ai": {
  "templateID": "patrol_and_chase",
  "resolution": {
    "attackAction": {
      "commands": [
        "entity.animate spear_thrust,once",
        "entity.emit meleeAttack"
      ]
    }
  }
}

This guard entity uses the patrol_and_chase tree but overrides the attackAction node with a custom spear thrust animation via the resolution system.
