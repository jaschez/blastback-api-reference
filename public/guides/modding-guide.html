Modding Guide

A practical guide to creating custom content for Blastback Engine. Learn how to build entities, weapons, UI elements, and more.

Prerequisites
Before diving in, make sure you have read the Getting Started guide and understand the basics of the Entity Scripting system.

Creating Custom Entities

Modding in Blastback Engine revolves around creating JSON entity files and composing them from existing components. To create a custom entity:

  1. Create a new JSON file in the Content/Entities/ directory with a descriptive name (e.g., fire_bat.mob.json).
  2. Define the base properties including name, visuals path, render layer, and physics configuration.
  3. Add components to give the entity its behavior -- movement, animation, AI, health, and weapons.
  4. Create a behavior tree if the entity needs AI (place it in Content/BehaviorTrees/ as bt.[ID].json).
  5. Add sprite assets to Content/Sprites/ in PNG, ASE, or Atlas format.

File Naming Convention

PatternModel TypeExample
[name].mob.jsonMob (enemies, NPCs)goblin.mob.json
[name].weapon.jsonWeaponlaser_rifle.weapon.json
[name].projectile.jsonProjectilefireball.projectile.json
[name].drop.jsonItem drophealth_potion.drop.json
fire_bat.mob.json
{
  "name": "Fire Bat",
  "visualsPath": "enemies/fire_bat",
  "renderLayer": 5,
  "colliderSizeX": 10,
  "colliderSizeY": 10,
  "physicsLayer": 3,
  "collisionLayerMask": [1, 2, 4],
  "components": {
    "animator": {
      "triggers": {
        "idle": {},
        "fly": {},
        "attack": { "hit": 3 }
      }
    },
    "ai": {
      "templateID": "flying_chase"
    },
    "mob": {
      "health": 20,
      "damage": 8
    },
    "movement": {
      "speed": 85.0
    },
    "levitation": {
      "amplitude": 3.0,
      "frequency": 2.0
    }
  },
  "model": {
    "id": "fire_bat",
    "namespc": "enemies"
  }
}
Tip
Start by duplicating an existing entity file that is similar to what you want to create, then modify the properties and components. This is faster than building from scratch and helps avoid missing required fields.

Working with the Component System

Components are added to the components object in your entity JSON. Each key is the component type identifier, and the value is its configuration.

Commonly Used Components

ComponentPurposeTypical Use
animatorSprite animation controlAll visual entities
movementPhysics-based movementCharacters, enemies, NPCs
steeringMovementAvoidance and flockingGroups of enemies
mobHealth, damage, knockbackEnemies and destructible props
aiBehavior tree connectionAutonomous entities
weaponHandlerWeapon equip and useArmed enemies and players
triggerEvent zone detectionInteractive areas, traps
spawnerEntity spawningSpawn points, generators
levitationFloating hover effectFlying enemies, floating items
inputPlayer input handlingPlayer entity only

Combining Components with commandMap

The power of the component system comes from composition. The commandMap system ensures components communicate through events rather than direct references, so any combination is valid.

Component combination example
"components": {
  "animator": { ... },
  "movement": { "speed": 50.0 },
  "mob": { "health": 100, "damage": 0 },
  "trigger": {
    "commandMap": {
      "onPlayerEnter": "entity.animate open,once",
      "onPlayerExit": "entity.animate close,once"
    },
    "events": {
      "onCollision": ["onPlayerEnter"],
      "onCollisionExit": ["onPlayerExit"]
    }
  },
  "interactionHandler": {
    "interactionKey": "E",
    "commandMap": {
      "onInteract": "entity.emit activate"
    }
  }
}

Creating Custom Weapons

Weapons in Blastback Engine are defined through a combination of models and components. The three key pieces are WeaponModel, ShooterComponent, and MeleeComponent.

WeaponModel

The WeaponModel defines the weapon's core data -- its name, damage, fire rate, visual representation, and projectile configuration.

plasma_cannon.weapon.json
{
  "name": "Plasma Cannon",
  "visualsPath": "weapons/plasma_cannon",
  "renderLayer": 4,
  "components": {
    "weaponComponent": {
      "damage": 20,
      "knockback": 80,
      "type": "ranged"
    },
    "shooterComponent": {
      "projectileEntity": "plasma_bolt",
      "fireRate": 0.4,
      "spread": 3.0,
      "burstCount": 1,
      "muzzleOffset": 8.0
    },
    "animator": {
      "triggers": {
        "fire": { "muzzleFlash": 1 }
      }
    }
  },
  "model": {
    "cooldown": 0.4,
    "maxAmmo": 30,
    "visual": {
      "sprite": "plasma_cannon",
      "scale": 1.0
    }
  }
}

ShooterComponent

For ranged weapons, the ShooterComponent handles projectile spawning, aiming, recoil, and ammunition.

ParameterTypeDescription
projectileEntitystringEntity ID of the projectile to spawn
fireRatefloatSeconds between shots
spreadfloatAngular spread in degrees for shot randomization
burstCountintNumber of projectiles per burst (1 for single shot)
burstDelayfloatDelay between burst projectiles
muzzleOffsetfloatSpawn offset for projectiles relative to weapon origin

MeleeComponent

For melee weapons, the MeleeComponent handles swing arcs, hit detection, and damage application. Melee attacks use the Melee Impacts physics layer (8) for hit detection.

battle_axe.weapon.json
{
  "name": "Battle Axe",
  "visualsPath": "weapons/battle_axe",
  "renderLayer": 4,
  "components": {
    "weaponComponent": {
      "damage": 35,
      "knockback": 150,
      "type": "melee"
    },
    "meleeComponent": {},
    "animator": {
      "triggers": {
        "swing": { "impact": 4 }
      }
    }
  },
  "model": {
    "cooldown": 0.8,
    "maxAmmo": -1,
    "visual": {
      "sprite": "battle_axe",
      "scale": 1.2
    }
  }
}
ParameterTypeDescription
damageintBase damage per hit
knockbackfloatKnockback force applied on hit
rangefloatReach distance of the melee attack
arcfloatSwing arc in degrees
attackDurationfloatDuration of the attack animation window
cooldownfloatTime before the weapon can attack again

Creating Projectiles

Projectiles are lightweight entities that travel in a direction and apply effects on collision.

plasma_bolt.projectile.json
{
  "name": "Plasma Bolt",
  "visualsPath": "projectiles/plasma_bolt",
  "renderLayer": 3,
  "colliderSizeX": 6,
  "colliderSizeY": 6,
  "isTrigger": true,
  "physicsLayer": 4,
  "collisionLayerMask": [1, 3],
  "model": {
    "speed": 200.0,
    "damage": 20,
    "lifetime": 3.0,
    "piercing": false,
    "gravity": 0.0
  }
}

Creating UI Elements

The engine provides 12 UI components for building in-game interfaces. UI elements are entities with specialized components that render on the screen layer rather than the world layer.

Available UI Components

ComponentPurpose
uiPanelBackground panel with configurable size, color, and opacity
uiLabelText display with font, size, color, and alignment options
uiImageStatic or animated image display
uiButtonInteractive button with hover, press, and click events
uiProgressBarHorizontal or vertical fill bar for health, loading, etc.
uiSliderDraggable slider for numeric value input
uiToggleOn/off toggle switch
uiListScrollable list of items
uiGridGrid layout container for inventory-style displays
uiTooltipContext-sensitive popup text on hover
uiDialogDialog box with text, portrait, and response options
uiMinimapMiniature map view with entity tracking
UI health bar example
{
  "name": "PlayerHealthBar",
  "visualsPath": "ui/health_bar",
  "renderLayer": 10,
  "components": {
    "uiPanel": {
      "width": 120,
      "height": 16,
      "color": "#1a1a2e",
      "opacity": 0.8
    },
    "uiProgressBar": {
      "width": 116,
      "height": 12,
      "fillColor": "#e74c3c",
      "backgroundColor": "#2c3e50",
      "value": 1.0,
      "bindTo": "player.health"
    }
  }
}
Note
UI entities use the same component system as game entities. You can combine UI components with event handling to create interactive menus, HUDs, and dialogs.

Tips and Best Practices

Entity Design

  • Keep entities focused. Each entity should represent one logical game object. Avoid putting unrelated behaviors on the same entity.
  • Use descriptive names. Entity names like fire_bat or health_potion_drop are easier to work with than entity_001.
  • Set appropriate physics layers. Only include layers in collisionLayerMask that the entity actually needs to interact with. Fewer collision checks means better performance.
  • Start simple. Begin with the minimum set of components and add complexity incrementally. Test after each change.

Performance

  • Use entity.onVisible to defer expensive operations until an entity is on screen.
  • Limit AI complexity for entities that appear in large numbers. Simple patrol trees are cheaper than complex multi-branch decision trees.
  • Reuse behavior tree templates with templateID instead of duplicating tree definitions. The engine caches resolved templates.
  • Prefer smaller collision radii when precise collision is not critical. Larger colliders require more collision checks.

Modding Workflow

  • Copy and modify existing entities rather than building from scratch. This ensures you do not miss required fields.
  • Use the AI editor at jaschez.github.io/blastback/ai-editor for behavior trees instead of hand-editing JSON.
  • Test incrementally. Add one component at a time and verify each works before adding the next.
  • Check the console for error messages if an entity does not behave as expected. The engine logs missing components, invalid parameters, and broken references.

Common Pitfalls

Watch Out For These

These are the most frequent issues encountered when modding Blastback Engine:

1. Missing or Mismatched Physics Layers

If your entity does not collide with anything, check that physicsLayer and collisionLayerMask are set correctly. Remember that collision is bidirectional -- both entities must include each other's layer in their mask.

2. Behavior Tree File Naming

BT files must be named bt.[ID].json. If you name a file slime_patrol.json instead of bt.slime_patrol.json, the engine will not recognize it as a behavior tree.

3. Invalid Visual Paths

The visualsPath must point to an existing asset in the Content/Sprites/ directory. Omit the file extension -- the engine resolves the correct format automatically. Use forward slashes for path separators.

4. Circular Template References

If behavior tree template A references template B, and template B references template A, the resolution system will fail. Always ensure template references form a directed acyclic graph.

5. Forgetting the commandMap

If you add a component that should respond to events but nothing happens, verify that the commandMap is properly configured. Commands are only routed to components that explicitly declare handlers for them.

6. Overlapping Collider Sizes

If colliders are too large relative to the sprite, entities will appear to collide before they visually touch. Match colliderSizeX and colliderSizeY to the sprite's actual hit area, not the full image bounds.

7. Animation Frame Mismatches

Trigger frame numbers in the animator component must match actual frames in the .ase file. If a trigger references frame 8 but the animation only has 6 frames, the event will never fire.
